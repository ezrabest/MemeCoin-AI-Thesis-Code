PATH NORMALIZATION AND ARTIFACT ID STABILITY

Do not build artifact_id from absolute paths.

All paths must be normalized as project-relative POSIX-style paths.

Example:

data/training/manual_verified_results/xgb_clean_full/file.parquet

Not:

E:\Projects\Final Project\memecoin_trader\data\...

Add and use these fields:

project_root
project_relative_path
path_id
logical_artifact_key
content_hash
artifact_id

Definitions:

project_root:
- detected repository/project root
- used only for computing relative paths
- do not include it in artifact_id

project_relative_path:
- path relative to project root
- use forward slashes
- do not include drive letters
- do not include machine-specific prefixes
- stable across Windows/Linux when project layout is the same

path_id:
- sha256("path:v1|" + project_relative_path)
- tracks the physical repository-relative file location

content_hash:
- sha256 of raw file bytes
- identifies file content

logical_artifact_key:
- deterministic string from available semantic metadata:
  phase + artifact_type + logical_name + model + filter + horizon + split + target_name + policy_name + consensus_tier
- unknown components should be omitted or set to "unknown"
- do not hallucinate metadata

artifact_id:
- sha256("artifact:v1|" + logical_artifact_key + "|" + content_hash)

Important:
- Lineage should prefer artifact_id/content_hash, not absolute file path.
- Store project_relative_path for human traceability.
- Store path_id separately for path-level duplicate detection.
- Do not use absolute path in artifact_id.
- artifact_id should remain stable across Windows-style and POSIX-style project roots when file content and logical metadata are the same.

HASHING RULES

Implement deterministic hash utilities.

content_hash:
- For ordinary files, hash raw file bytes with SHA-256.
- For large files, stream in chunks.
- Do not load entire large files into memory.
- content_hash is required unless hashing failed or was skipped by explicit size limit.

hash_status allowed values:
- computed
- reused_from_cache
- failed
- skipped_by_size_limit

When content_hash is missing:
- validation should emit ERROR unless the artifact has warning HASH_UNAVAILABLE or HASH_SKIPPED_BY_SIZE_LIMIT and hash_status explains why.

schema_hash:
- For CSV/Parquet tabular artifacts, hash normalized schema only.
- Do not hash full row contents for schema_hash.
- content_hash still covers the actual file bytes.

HASH CACHING / SHORT-CIRCUIT HASHING

The registry scanner must load the existing registry if present.

Before recalculating expensive hashes, check whether the same project_relative_path already exists in the previous registry.

If all of the following are unchanged:

- size_bytes
- modified_time_ns
- extension
- project_relative_path

Then reuse the previous:

- content_hash
- schema_hash
- row_count
- column_count
- columns
- raw_dtypes
- normalized_dtypes

Do not recalculate file SHA-256.
Do not reload the tabular file.
Do not recompute row_count/schema_hash.

Add CLI option:

--force-rehash

When --force-rehash is provided:
- ignore hash cache
- recompute content_hash and schema_hash

Use stat().st_mtime_ns rather than low-precision modified time where available.

Still write modified_time_utc for human readability.

If cache reuse occurs:
- hash_status = reused_from_cache
- metadata.cache_reused = true

If hash is recomputed:
- hash_status = computed
- metadata.cache_reused = false

If hashing fails:
- hash_status = failed
- content_hash = null
- add warning HASH_UNAVAILABLE
- continue scanning other artifacts

If hashing is skipped by size limit:
- hash_status = skipped_by_size_limit
- content_hash = null
- add warning HASH_SKIPPED_BY_SIZE_LIMIT
- continue scanning other artifacts

SCHEMA HASH DTYPE NORMALIZATION

For CSV/Parquet artifacts, store both raw and normalized dtypes.

raw_dtypes:
- exact dtype strings as reported by pandas/pyarrow reader

normalized_dtypes:
- stable dtype classes used for schema_hash

Normalization rules:

Integer dtypes:
- int8, int16, int32, int64, nullable Int64 -> int64

Unsigned integer dtypes:
- uint8, uint16, uint32, uint64 -> uint64

Float dtypes:
- float16, float32, float64, nullable Float64 -> float64

Boolean dtypes:
- bool, boolean -> bool

Datetime dtypes:
- datetime64[ns], datetime64[us], timezone-aware datetime -> datetime64[ns]

String-like dtypes:
- string, object containing strings -> string_or_object

Categorical:
- category -> category

Unknown/mixed/object:
- object -> object

schema_hash must be computed from:
- ordered column names
- normalized dtype strings

Do not compute schema_hash from raw dtype strings alone.

This prevents false schema changes caused by pandas/pyarrow/platform differences.

Preserve raw_dtypes in metadata so real debugging remains possible.
